**Task.** Run `facebook/detr-resnet-50` on video sampled at 2 fps and output one person score per frame: the max person probability over DETR's 100 queries. A frame with a score of **0.8** or more is "person" (`THRESHOLD` in `person_detector.py`). The same threshold applies to the stock pipeline and the optimized detectors.

**Setup.** The first 1024 sampled frames (about 512 s) of one 1080p recording, one NVIDIA H100. Frames are decoded once and shared, so every backend scores the same pixels. Each backend runs in its own process: 3 warmup passes, 3 timed passes, median reported. Model-only numbers come from an earlier sweep on 240 frames and are labeled as such.

**Quality** means drift from the stock pipeline's own output. There are no hand labels, so "recall" means "agrees with stock when stock says person". Numbers are measured unless marked **(inferred)** or **(computed)**.

## TL;DR

**Problem: the model was not the bottleneck.**

- CPU preprocessing was about **76%** of the per-frame time (73 to 77% across three runs, 83% on an earlier 480p run). The fp32 model was 23%.
- Inside the model, memory-bound elementwise ops (`add`, `mul`, `relu_`, `add_`) were **46.8%** of GPU time, more than convolutions (25.4%).

**Fixes and results.**

| Bottleneck | Fix | Result |
|---|---|---|
| CPU preprocessing | Resize and normalize on the GPU | 19.2 → 1.40 ms / frame |
| BatchNorm kernels | Fold BN into the conv weights | Exact; removes 2 kernels per conv |
| fp32 bytes, NCHW layout | fp16 + channels-last | 1.95x model-only (with the BN fold) |
| Many small pointwise kernels | `torch.compile(max-autotune)`, batch 16 | Model 5.78 → 0.98 ms / frame |

**End to end (1080p, H100).**

| Pipeline (backend) | Detector fps | Speedup | fps with decode |
|---|---|---|---|
| Stock (`hf_baseline`) | 38.7 | 1.0x | 18.8 |
| GPU preprocess only (`torch_reference`) | 138.2 | 3.6x | 28.9 |
| Model fixes only (`torch_hfpre`) | 62.0 | 1.6x | 23.0 |
| **Both (`torch`, my pick)** | **426.7** | **11.0x** | **33.6** |

Section 4 explains what each backend is.

- **Each fix alone is capped by the other stage. Together they multiply.**
- **Decode is now the limit.** Single-threaded OpenCV takes 27.4 ms per frame, which caps the end-to-end gain at 1.8x.
- **Fewer kernels, not faster kernels.** Kernel launches per frame fell from 132.8 to 22.7, and about 72% of the saved GPU time was pointwise ops.

**Quality and decision.**

- **`torch` matches the stock output closely.** At threshold 0.8 it flips 5 of 1024 frames: 4 misses and 1 false alarm, recall 0.992, precision 0.998, interval IoU 0.9834. Every optimized backend passes both quality checks.
- **The small drift comes from the GPU resize, not the model.** GPU preprocessing moves scores 8x more than the model changes. Few frames sit near 0.8, so only 5 flip: the same 5 in every GPU-preprocessing backend.
- **I picked `torch` at 0.8.** TensorRT adds only 0.3 fps end to end and has the same quality. Recall is my priority, and at 0.8 `torch` misses only 4 frames (recall 0.992).

## 1. Profile: where the time went

### Pipeline stages

| Stage (stock, batch 8, 1080p) | ms / frame | Share |
|---|---|---|
| **Preprocess** (`to_pil` 1.82 + HF processor 17.38) | **19.2** | **76%** |
| Model (fp32 eager) | 5.78 | 23% |
| Postprocess | 0.37 | 1% |
| Decode (outside the detector) | 27.4 | n/a |

> **Bottleneck 1: CPU preprocessing.** `cProfile` of the HF processor shows `normalize` at 34% and `resize` at 29%. Both run in float32 numpy, one frame at a time, on one core.

Amdahl check (480p run): an infinitely fast model would speed the pipeline up by at most **1.14x**. So preprocessing comes first.

### Inside the model

`torch.profiler` on the fp32 eager model, share of CUDA time:

| Op group | Share | Note |
|---|---|---|
| **Elementwise: `add`, `mul`, `relu_`, `add_`** | **46.8%** | Many small kernels (34 to 82 us), each reading and writing a whole activation. The `mul` / `add` pairs are DETR's frozen BatchNorm **(inferred)** |
| Convolutions | 25.4% | |
| Linear layers | 9% | |

> **Bottleneck 2: memory-bound pointwise ops.** They do almost no math. Each one reads a whole activation tensor and writes it back, so memory bandwidth sets the time, not FLOPs.

Other profile facts:

- **By block:** the ResNet-50 backbone is 67% of model time, the encoder 17% and the decoder 15%.
- **Batch size:** going from batch 1 to 4 cuts per-frame model time from 26.7 to 6.9 ms. From 4 to 16, fps gains only 2% and 1.5% while memory doubles, so the GPU is saturated by batch 8.

<details>
<summary>How I timed it (<code>profile_detector.py</code>)</summary>

CUDA launches are asynchronous. Without synchronization you time the launch, not the kernel.

```python
@contextmanager
def _timed(stats, name):
    torch.cuda.synchronize()          # without this you time the launch, not the kernel
    t0 = time.perf_counter()
    yield
    torch.cuda.synchronize()
    stats[name] += time.perf_counter() - t0
```

- **One subprocess per backend**, so compile caches and peak memory are not shared.
- **Warmup passes first**, so `torch.compile` autotuning and the TensorRT engine build are not in the timed passes.
- **Peak GPU memory is polled from the driver** (`torch.cuda.mem_get_info`), because `torch.cuda.max_memory_allocated()` does not see TensorRT's own allocations. It is device-wide, so other processes on the GPU would be counted.
- **Wait for a free GPU before starting.** A worker from a stopped run can still hold the GPU, and a backend started then dies with CUDA out of memory. That cost one run its baseline, so the script now waits up to 120 s for 16 GB of free GPU memory and otherwise fails with the process list.

</details>

<details>
<summary>The stock pipeline code (<code>_HfBackend</code> in <code>profile_detector.py</code>)</summary>

Every "before" snippet below is a piece of this.

```python
def _score(self, batch_bgr, stats):
    with _timed(stats, "to_pil"):
        images = [Image.fromarray(cv2.cvtColor(f, cv2.COLOR_BGR2RGB)) for f in batch_bgr]
    with _timed(stats, "preprocess"):
        inputs = self._processor(images=images, return_tensors="pt").to("cuda")   # CPU: HF processor
    with _timed(stats, "model"), torch.no_grad():

    with _timed(stats, "postprocess"):

            out, threshold=0.0, target_sizes=sizes
        )
        scores = []
        for r in results:
            mask = r["labels"] == self._person_id
            scores.append(r["scores"][mask].max().item() if mask.any() else 0.0)  # one .item() per frame
    return scores
```

</details>

## 2. The fixes

Fixes 1 and 2 move CPU work to the GPU. Fixes 3 to 6 target bottleneck 2.

### Fix 1: preprocess on the GPU

- **Problem:** the HF processor runs on the CPU and costs 19.2 ms per frame (16.7 to 20.1 ms across runs).
- **Change:** upload raw uint8 once per batch (1 byte per value instead of 4), then flip, resize and normalize as tensor ops on the GPU.
- **Result:** **1.40 ms per frame**, about 14x less **(computed)**. On its own this gives a 3.6x detector speedup.

```python
# BEFORE (stock): CPU HF processor, then a copy to the GPU
inputs = self._processor(images=images, return_tensors="pt").to("cuda")

# AFTER (person_detector.py): one uint8 upload, then tensor ops on the GPU
x = torch.from_numpy(np.stack(batch)).to(self._device)   # upload uint8 (1 byte/px); float comes after the copy
x = x.permute(0, 3, 1, 2).flip(1).float()                 # NHWC -> NCHW, BGR -> RGB, on the GPU
target = self._resize_target(*batch[0].shape[:2])         # exact size the HF processor would use (750x1333)
# antialias=True matches PIL / torchvision when shrinking; without it the resize aliases and scores drift
x = F.interpolate(x, size=target, mode="bilinear", align_corners=False, antialias=True)
x = x.round().clamp(0, 255)                               # re-quantize to uint8 like the CPU path
x = (x / 255.0 - self._mean) / self._std                  # same normalization as the HF processor
```

**`antialias=True` matters.** Without it, the resize differs from the HF processor by up to 86 levels (of 255). With it, the difference is at most 1 level. That 1 level is the source of the score drift in section 5. The remaining 1.40 ms is probably `np.stack` plus the pageable host-to-device copy **(inferred, not timed)**.

### Fix 2: postprocess on the GPU

- **Problem:** the stock postprocess builds boxes for every frame in a Python loop, then calls `.item()` once per frame.
- **Change:** softmax and top-1 on the GPU (softmax in fp32, even with an fp16 model), then one copy per batch.
- **Result:** a small win. Stock postprocess was 0.37 ms per frame.

```python
# BEFORE (stock): HF post-processing, then one .item() per frame
results = self._processor.post_process_object_detection(out, threshold=0.0, target_sizes=sizes)
for r in results:
    mask = r["labels"] == self._person_id
    scores.append(r["scores"][mask].max().item() if mask.any() else 0.0)

# AFTER (person_detector.py): reduce on the GPU, one copy per batch
prob = logits.float().softmax(-1)[..., :-1]            # softmax in fp32 even when the model ran fp16
top_score, top_label = prob.max(-1)                    # best class per query, on the GPU
person = torch.where(top_label == self._person_id, top_score, torch.zeros_like(top_score))
return person.max(dim=1).values.cpu().tolist()         # ONE score per frame, one copy per batch
```

### Fix 3: fold BatchNorm into the conv

- **Problem:** frozen BatchNorm runs as separate `mul` and `add` kernels after each of the 53 convs.
- **Change:** in eval mode BN is a fixed per-channel affine map, so fold it into the conv's weights and bias. The result is **exact**, not approximate.
- **Result:** two memory-bound kernels removed per conv. Measured together with Fix 4.

```python
# BEFORE: conv, then BN as two extra elementwise kernels
y = (conv(x) - mean) * w / sqrt(var + eps) + b

# AFTER (torch_detector.py): one conv with rescaled filters and a new bias
fold_frozen_bn(model)                                          # all 53 conv + BN pairs
scale = bn.weight * (bn.running_var + eps).rsqrt()             # per conv: per-output-channel multiplier
fused.weight.copy_(conv.weight * scale.view(-1, 1, 1, 1))
fused.bias.copy_((bias - bn.running_mean) * scale + bn.bias)
```

### Fix 4: fp16 + channels-last

- **Problem:** fp32 doubles the bytes moved by a memory-bound model. In NCHW layout, tensor-core convs need layout transposes.
- **Change:** cast the weights and input to fp16. Convert the weights and input to channels-last once.
- **Result (Fixes 3 + 4, eager, model-only):** **185 → 362 fps, 1.95x**, quality gate passed. The three changes were not measured separately.

```python
# BEFORE (stock): fp32 weights and input, NCHW
self._model = DetrForObjectDetection.from_pretrained(MODEL_ID).eval().to("cuda")

# AFTER (torch_detector.py)
model = model.to(memory_format=torch.channels_last)   # NHWC: tensor-core convs skip layout transposes
model = model.to(torch.float16)                       # half the bytes per tensor, tensor-core math

# ... and the input, at the end of _preprocess
layout = torch.channels_last if self._channels_last else torch.contiguous_format
return x.to(self._input_dtype).contiguous(memory_format=layout)
```

<details>
<summary>Why channels-last helps</summary>

**Tensors carry strides, not just a shape.** The same logical `(N, C, H, W)` tensor can be laid out in memory two ways:

```python
x = torch.zeros(1, 3, 4, 4)
x.stride()                                                   # (48, 16, 4, 1)  W is contiguous: NCHW
y = x.contiguous(memory_format=torch.channels_last)
y.shape, y.stride()                                          # same shape, (48, 1, 12, 3)  C is contiguous: NHWC
```

**Tensor cores want the reduction dimension contiguous.** A convolution runs as an *implicit GEMM*: output pixels are the rows (`M`), output channels the columns (`N`), and the reduction runs over `C*R*S` (`K`). The `K` dimension of the activation matrix is the input channel.

```cuda
// NHWC: channels are contiguous, so one thread loads 8 fp16 channels (16 bytes) in one instruction
int4 v = *(int4*)&input[((n*H + h)*W + w)*C + c0];

// NCHW: channels are H*W elements apart, so the K dimension becomes a strided gather
for (int i = 0; i < 8; ++i)
    a[i] = input[((n*C + c0 + i)*H + h)*W + w];
```

**The kernel choice happens on the CPU.** PyTorch and cuDNN look at the shape, strides and dtype, then pick a kernel. Given NCHW, cuDNN launches a slower kernel or wraps the conv in layout transposes, which are pure memory traffic.

**Convert once.** Most CNN ops preserve their input's memory format, so setting it on the input and weights propagates through the network.

</details>

### Fix 5: kernel fusion with `torch.compile`

- **Problem:** each remaining pointwise op is its own kernel and its own round trip to memory.
- **Change:** `torch.compile(mode="max-autotune")` fuses the remaining pointwise ops into Triton kernels and benchmarks conv / matmul tile sizes against cuDNN / cuBLAS.
- **Result (model-only):** 362 → **958 fps** at batch 8, and **1058 fps (5.70x)** at batch 16.

```python
# BEFORE (stock): eager, one kernel launch per op
out = self._model(**inputs)

# AFTER (torch_detector.py)
model = torch.compile(model, mode="max-autotune")
# Compiled graphs are specialised to one input shape: fixed batch, or every new batch size recompiles.
```

| Compile mode (model-only, batch 8) | What it adds | fps |
|---|---|---|
| none (eager, after Fixes 3-4) | one launch per op | 362 |
| `default` | fuses pointwise ops | 811 |
| `max-autotune` | + benchmarks conv / matmul tiles | **958** |
| CUDA graphs | + replays recorded launches | 836 |

**CUDA graphs add nothing over default compile.** They remove CPU launch overhead, and launch overhead was not the bottleneck.

<details>
<summary>What fusion actually does</summary>

Take BN scale, add bias, add residual, ReLU (`T` = tensor size):

```python
# Eager: 4 kernels, each reads and writes whole tensors
#   x*scale: 2T,  +bias: 2T,  +res: 3T,  relu: 2T   ->  about 9T of memory traffic
y = x * scale; y = y + bias; y = y + res; y = torch.relu(y)

# Fused: one kernel reads x and res once, keeps intermediates in registers, writes once -> about 3T
@triton.jit
def fused(x_ptr, res_ptr, scale_ptr, bias_ptr, out_ptr, n, C, HW, BLOCK: tl.constexpr):
    offs = tl.program_id(0) * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    x = tl.load(x_ptr + offs, mask=mask)
    res = tl.load(res_ptr + offs, mask=mask)
    c = (offs // HW) % C
    y = x * tl.load(scale_ptr + c, mask=mask) + tl.load(bias_ptr + c, mask=mask) + res
    tl.store(out_ptr + offs, tl.maximum(y, 0.0), mask=mask)
```

Pointwise ops do almost no arithmetic, so their time follows memory traffic. Cutting 9T to 3T is the whole trick. In the profile, fusion shows up in kernel names such as `triton_poi_fused_add_relu`. `TORCH_LOGS=output_code` prints the generated Triton code.

</details>

### Fix 6: fixed-shape batching and warmup

- **Problem:** the stock eager model accepts any batch size, so the last batch can be short. A compiled graph or a TensorRT engine is fixed to one input shape, so a short batch would recompile or break the engine.
- **Change:** use batch 16, pad the short last batch with its final frame, drop the padded scores, and warm up before timing.
- **Result:** batch 16 beats batch 8 by about 10% (1058 vs 958 fps). Batch 32 adds nothing.

```python
# BEFORE (stock): the last chunk can be short, which is fine for an eager model
for chunk in _chunks(frames, backend.batch_size):
    rep_scores += backend.score(chunk)

# AFTER (person_detector.py): pad the short last batch with its final frame, then drop the padded scores
batch += [batch[-1]] * (size - real)
# warmup(): run full batches of one real-shaped frame so compile / engine build finish before timing.
```

An earlier sweep on 240 frames. Every variant gets the same preprocessed input, and decode and preprocessing are not timed, so this measures the model alone. Every row passed the quality gate against fp32 eager, except the ONNX Runtime TensorRT provider.

### Rejected options

**Direct TensorRT.** Model-only it is the fastest: 1417 fps, 1.34x the `torch` model. End to end it adds only 10% detector fps (471.7 vs 426.7) and 0.3 fps with decode (33.9 vs 33.6). Its quality is the same as `torch`: the same 5 flipped frames (section 5). The engine is tied to one GPU model, TensorRT version, batch size and input size, and the cold build took 146 s. Worth revisiting only if the GPU type is fixed and decode stops being the limit. Pinning the softmax and normalization layers to fp32 changed nothing, so fp16 in those layers is not a quality problem.

**ONNX Runtime's TensorRT provider.** Fast (1255 fps) but **wrong outputs**: agreement 0.929 and IoU 0.878 against fp32. Two checks place the fault inside the provider:

- The same ONNX file built directly with TensorRT passes the gate.
- `polygraphy run model.onnx --trt --onnxrt` agrees to 2.5e-5.

So the fault is in the provider's graph partitioning, not in the model or in TensorRT. ONNX Runtime's CUDA provider was not competitive either: 1.2x with fp32, 1.8x with fp16.

## 3. Why the model got faster

| Per frame | fp32 eager | `torch` |
|---|---|---|
| Kernel launches | 132.8 | 22.7 |
| Average kernel time | about 39 us | about 40 us |

Of the 4.32 ms per frame saved, **about 72% was pointwise ops**, removed by BN folding and fused by the compiler.

> **Fewer kernels, not faster kernels.** The average kernel got no faster. The baseline was memory-bound on pointwise ops, and folding plus fusion removed them.

## 4. End-to-end results

### The five backends

A backend is one complete detector: BGR frames in, one person score per frame out. The backends differ in two switches: where preprocessing runs, and which model runs.

| Backend | Preprocess | Model | Batch | What it is | Question it answers |
|---|---|---|---|---|---|
| `hf_baseline` | CPU (HF processor) | fp32 eager | 8 | The stock pipeline as it runs today | None. It is the reference for speed and for quality |
| `torch_reference` | GPU | fp32 eager | 8 | The stock model behind the new GPU preprocessing | What does GPU preprocessing alone change? |
| `torch_hfpre` | CPU (HF processor) | fp16, folded BN, channels-last, compile | 16 | The optimized model behind the stock preprocessing | What do the model fixes alone change? |
| **`torch`** | **GPU** | **fp16, folded BN, channels-last, compile** | **16** | **The optimized torch detector (my pick)** | **What do both fixes give together?** |
| `tensorrt` | GPU | fp16 TensorRT engine | 16 | The same GPU preprocessing, with a TensorRT engine instead of the torch model | Is TensorRT worth it over `torch`? |

`torch_reference` and `torch_hfpre` are not candidates for production. They exist only to change one switch at a time:

```text
                      stock model (fp32 eager)    optimized model
CPU preprocessing     hf_baseline                 torch_hfpre
GPU preprocessing     torch_reference             torch      (tensorrt: same row, TensorRT engine)
```

- **Moving down a column** changes only the preprocessing: `hf_baseline` → `torch_reference`.
- **Moving across a row** changes only the model: `hf_baseline` → `torch_hfpre`.
- **The batch sizes differ:** backends with the stock model use batch 8, the optimized ones 16. About 10% of the model-level gain is batch size.

<details>
<summary>How the backends are built (<code>profile_detector.py</code>)</summary>

```python
def _build_backend(name, trt_engine_dir):
    if name == BASELINE:                                      # "hf_baseline"
        return _HfBackend()                                   # the stock path: HF processor + fp32 eager
    if name == "torch_reference":
        return _DetectorBackend(create_detector(REFERENCE_CONFIG))   # GPU preprocessing, fp32 eager
    if name == "torch_hfpre":
        return _DetectorBackend(_HfPreTorchDetector(TorchConfig()))  # optimized model, HF preprocessing
    if name == "torch":
        return _DetectorBackend(create_detector(TorchConfig()))      # the optimized detector
    if name == "tensorrt":
        return _DetectorBackend(create_detector(TensorRTConfig(engine_dir=trt_engine_dir)))
```

`torch_hfpre` is the optimized torch detector with only its preprocessing swapped back to the stock HF processor:

```python
class _HfPreTorchDetector(TorchPersonDetector):
    """The optimized torch model behind the baseline's preprocessing, to separate the two."""

    def _preprocess(self, batch):
        images = [Image.fromarray(cv2.cvtColor(f, cv2.COLOR_BGR2RGB)) for f in batch]
        x = self._hf_processor(images=images, return_tensors="pt")["pixel_values"].to(self._device)
        layout = torch.channels_last if self._channels_last else torch.contiguous_format
        return x.to(self._input_dtype).contiguous(memory_format=layout)
```

Each backend runs in its own subprocess, on the same pre-decoded frames.

</details>

### Results

| Backend | Pre ms | Model ms | Detector fps | Speedup | fps with decode |
|---|---|---|---|---|---|
| `hf_baseline` | 19.2 | 5.78 | 38.7 | 1.00x | 18.8 |
| `torch_reference` | 1.51 | 5.76 | 138.2 | 3.57x | 28.9 |
| `torch_hfpre` | 15.53 | 0.98 | 62.0 | 1.60x | 23.0 |
| **`torch`** | **1.40** | **0.98** | **426.7** | **11.03x** | **33.6** |
| `tensorrt` | 1.43 | 0.70 | 471.7 | 12.19x | 33.9 |

- **Pre ms:** for `hf_baseline` it includes `to_pil` (1.82 ms), and it has another 0.37 ms of postprocess. For the optimized backends, softmax, top-1 and the copy to host are not broken out.
- **fps with decode** adds decode to each frame, decoded then detected one after the other: `1000 / (1000 / detector_fps + decode_ms)`.

What this shows:

- **Together they multiply.** The model fixes make the model 5.9x faster (5.78 → 0.98 ms), but with CPU preprocessing still at 15.5 ms the pipeline gains only 1.6x. GPU preprocessing alone gives 3.6x. Both give 11.0x.
- **Decode is the end-to-end limit.** Decode costs 27.4 ms per frame, so the pipeline goes from 18.8 to 33.6 fps, only **1.79x**. **(computed)** One H100 at 427 fps could serve about 12 decoders of 36 fps each, so the detector work pays off once decode runs in parallel across cores.
- **Model numbers match the model-only sweep:** `torch` about 1020 fps (sweep: 1058), `tensorrt` about 1430 fps (sweep: 1417).
- **Run-to-run noise is about ±10%.** The `torch` speedup was 10.27x (256 frames), then 10.59x, 9.69x and 11.03x in three 1024-frame runs. The baseline ran at 38.7 to 43.0 fps on a shared host. Treat the speedup as 10x to 11x.
- **Cold start:** `torch.compile` took 84.5 s to warm up on a cold cache in the first run and 5.4 s with a warm cache. The TensorRT engine build took 146 s cold.

## 5. Quality: drift from the stock pipeline

**Terms.** The stock pipeline is the reference.

| Term | Meaning |
|---|---|
| **Threshold** | The score cutoff that turns a score into person / no person: 0.8, for stock and optimized alike |
| **Flip** | A frame where the two pipelines disagree on person / no person |
| **Miss** | Stock says person, the new pipeline says no person. Lowers recall |
| **False alarm** | Stock says no person, the new pipeline says person. Lowers precision |

A flip means "different from stock", not "wrong". There are no labels.

### Few frames sit near 0.8

At 0.8 the stock pipeline flags **476 frames (46%) as person, in 9 intervals**. Because only 19 frames are close to the line, small score noise can flip only a few flags.

### Where the drift comes from: the GPU preprocessing

- **Scores:** `torch_hfpre` (optimized model, CPU preprocessing) differs from the stock scores by 0.0015 on average (max 0.051). `torch_reference` (GPU preprocessing, fp32 model) differs by 0.012 (max 0.22), **8x more**. The model changes are clean.
- **Why the GPU resize differs (partly inferred).** On one synthetic 1080p frame the GPU path is within 1 level of 255 of the HF processor (mean 0.17, about 9% of pixels one level off). That leftover level comes from torchvision's integer uint8 resize kernel, which a float resize cannot reproduce **(inferred)**.
- **At 0.8 that drift flips only 5 frames,** because the threshold sits where almost no scores are.

### The quality gate

The gate is interval IoU ≥ 0.95, with flags merged over 1 s and segments under 0.5 s dropped, because intervals are what production consumes. Flag agreement is reported and warned on below 0.99, and `--strict-flags` requires both. At 0.8 every optimized backend passes both.

```python
flag_agreement = ((base >= THRESHOLD) == (new >= THRESHOLD)).mean()        # THRESHOLD = 0.8
iou = interval_iou(to_intervals(new, step_s), to_intervals(base, step_s))   # what the gate uses
passed = iou >= MIN_INTERVAL_IOU and (flag_agreement >= MIN_FLAG_AGREEMENT or not strict_flags)
```

- **The gate has headroom at 0.8.** The IoU margin is +0.033, and flag agreement allows 10 flips where `torch` has 5.
- **A short window can still fall under it.** Per-window IoU for `torch` over four windows is 0.969, 1.000, 1.000 and 0.862. The last window holds three of the five flips (frames 824, 826 and 915).
- **It reproduced.** The real run gave the same five flipped frames for all three GPU-preprocessing backends. An earlier recomputation from the previous run's scores had one extra `torch` flip, frame 118 (stock 0.788, `torch` 0.800, right on the threshold), so run-to-run noise near the threshold costs about one frame. The likely cause is `max-autotune` picking different kernels between runs, so compiled fp16 scores are not exactly repeatable **(inferred)**.

## 6. Decision: `torch` at threshold 0.8

**Why `torch`:**

- 10x to 11x detector speed, and 1.8x end to end with decode.
- Drift identical to GPU preprocessing alone: recall 0.992 and precision 0.998 against the stock flags.
- No engine to build, cache or rebuild per GPU, version, batch or input size. TensorRT adds only 0.3 fps end to end, with the same quality.

The stock pipeline stays in the package for later end-to-end benchmarks. Both are detectors behind one interface:

```python

from src.bayleef.person_detection.hf_baseline_detector import HfBaselineConfig

# also by name: create_detector_by_name("hf_baseline") / ("tensorrt"), same names as profile_detector.py
detector.warmup(frame_bgr)                                 # compile / engine build before timing
scores = detector.person_scores(frames_bgr)                # one person score per BGR uint8 frame; apply THRESHOLD yourself
```

**Recall is my priority.** At 0.8, `torch` misses 4 of the 476 frames stock calls person (recall 0.992).

## Key concepts, one line each

| Concept | One-line explanation |
|---|---|
| Profile before optimizing | The model was a quarter of the time; Amdahl capped model-only work at 1.14x |
| Memory-bound ops | Pointwise ops do almost no math, so bytes moved set their time |
| BN folding is exact | Eval-mode BN is a per-channel affine map, which merges into the conv's weights and bias |
| fp16 | Halves the bytes on a memory-bound model and enables tensor cores |
| Channels-last | Makes the conv's reduction dimension (channels) contiguous, so no layout transposes |
| Fusion | One kernel instead of a chain: about 9T to 3T of memory traffic in the BN + residual + ReLU example |
| CUDA graphs did nothing | They remove launch overhead, which was not the bottleneck |
| Fixed shapes | A compiled graph or TensorRT engine is tied to one input shape, so pad the last batch |
| Quality gate | A faster wrong answer is not a speedup; it caught the ONNX Runtime bug |
| Isolation backends | `torch_hfpre` and `torch_reference` showed the drift comes from the GPU resize, not the model |
| Threshold placement | At 0.8 few stock scores sit near the line, so small score drift flips few frames |
